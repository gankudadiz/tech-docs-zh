# 02. 技术栈与架构决策

**日期**: 2026-05-16  
**当前状态**: 首期推荐方案已确定

## 1. 结论

首期推荐使用：

- Docusaurus 3
- TypeScript
- React
- MDX
- 本地静态构建

本项目暂不需要数据库和后台管理系统。原因很直接：当前核心问题是“文档内容如何采集、翻译、按产品和版本组织、可搜索地阅读”，不是“业务数据如何管理”。

## 2. 为什么不是先做后台

后台管理适合这些场景：

- 多人分配翻译任务。
- 页面需要审核流和修改记录。
- 术语表需要审批。
- 需要登录、权限、统计、发布队列。
- 需要把翻译任务和 AI 调用记录结构化存储。

当前阶段只有本地维护和阅读，使用 Markdown/MDX + Git 文件历史更轻，也更容易长期迁移。过早上 Laravel + Filament 会把重点从内容质量转移到管理功能。

## 3. 为什么推荐 Docusaurus

Docusaurus 更贴合当前需求：

- 官方支持文档版本化，能保留不同版本的文档目录。
- 支持版本下拉，适合 `Filament v3.x / v4.x / v5.x` 这种形态。
- 支持 i18n 和 Markdown/MDX 内容组织。
- 构建结果是静态站，可以只在本地使用。
- React/MDX 生态成熟，后续做自定义首页、产品入口、来源提示组件比较方便。

官方 Docusaurus 版本化文档说明，版本会通过 `docs/`、`versioned_docs/`、`versioned_sidebars/` 和 `versions.json` 组织；导航也提供 `docsVersionDropdown` 用于版本下拉。

## 4. 为什么暂不选 Astro Starlight

Astro Starlight 很适合轻量文档站：

- 内置多语言路由和 fallback。
- 默认集成 Pagefind 全文搜索。
- 可以按文件系统自动生成侧边栏。

但它没有像 Docusaurus 那样直接围绕“多版本文档 + 版本下拉”提供完整约定。这个项目最强调“多个产品、每个产品多个版本”，所以首期更适合选择 Docusaurus。

如果后续发现版本管理完全可以手写，且希望页面更轻、构建更简单，可以再评估 Starlight。

## 5. UI 是否要和官方完全一致

不建议完全一致。

建议策略是“阅读结构相似，视觉系统独立”：

- 保留官方文档的信息结构，例如目录分组、页面顺序、代码示例位置。
- 不复制官方品牌 UI、图标、专有插画、主题样式。
- 可以在产品入口页使用产品名和版本信息，但要避免让人误以为这是官方站。
- 译文页应明确标注来源、采集日期、翻译状态和非官方汉化说明。

这样既能降低版权和商标风险，也能让多个产品入口保持统一阅读体验。

## 6. 本地端口

约定冷门本地端口：

```text
127.0.0.1:48763
```

避免使用常见端口：

- `3000`
- `5173`
- `8000`
- `8080`
- `9000`

## 7. 后续架构演进

首期：

```text
Markdown/MDX 源文件 -> Docusaurus 静态站 -> 127.0.0.1:48763
```

中期：

```text
官方文档源 -> 采集脚本 -> 清洗后的 Markdown/MDX -> AI 初译 -> 人工校对 -> 静态站
```

后期如需管理端：

```text
Laravel + Filament 管理翻译任务
              |
              v
       导出 Markdown/MDX
              |
              v
       Docusaurus 静态站
```
