# 06. 代码注释增强工作流

**日期**: 2026-05-21  
**状态**: 正式

本文档定义翻译校对之后的代码注释增强流程。目标是：**在不改变示例代码行为和可复制性的前提下，基于英文源文件与中文译文的对照理解，为文档中的示例代码补充尽可能充分、详细、准确的中文注释**。

本流程适用于已经完成翻译、且已按 `03_翻译校对工作流.md` 通过基础校对的文档。代码注释增强不是重新翻译正文，也不是重写示例代码；它是在保留原示例意图的基础上，让中文读者阅读代码块时不必频繁回看正文或英文原文。

---

## 0. 执行前变量

执行前先确认变量，后续命令都按变量替换：

| 变量 | 示例 | 说明 |
|------|------|------|
| `{product}` | `{product}` | 产品或框架目录名 |
| `{version}` | `{version}` | 版本目录名 |
| `{lang}` | `zh-cn` | 翻译语言 |
| `{source_file}` | `sources/{product}/{version}/normalized/docs/{source_relative_path}.md` | 英文源文件 |
| `{content_file}` | `content/{product}/{version}/{lang}/docs/{published_relative_path}.md` | 中文归档文件 |
| `{site_file}` | `site/docs/{product}/{version}/{published_relative_path}.md` | 站点可见文件 |
| `{site_docs}` | `site/docs/{product}/{version}` | 当前产品/版本站点目录 |

执行命令前可先设置：

```bash
PRODUCT="{product}"
VERSION="{version}"
LANG=zh-cn
SOURCE_FILE="sources/$PRODUCT/$VERSION/normalized/docs/{source_relative_path}.md"
CONTENT_FILE="content/$PRODUCT/$VERSION/$LANG/docs/{published_relative_path}.md"
SITE_FILE="site/docs/$PRODUCT/$VERSION/{published_relative_path}.md"
SITE_DOCS="site/docs/$PRODUCT/$VERSION"
```

不同产品、框架或语言的源文件组织方式可能不同。执行本流程时，应先根据该产品/版本的采集记录、source-structure 说明或现有目录映射，确认 `{source_file}` 与 `{content_file}` / `{site_file}` 的对应关系，不要套用其他框架的路径结构。

---

## 1. 适用范围

### 1.1 应处理的代码块

优先处理这些代码块：

- [ ] `php`、`blade`、`js`、`ts`、`tsx`、`css` 等示例代码
- [ ] `bash` / `shell` 命令示例中含有多个步骤、参数或环境变量的片段
- [ ] `yaml`、`env`、`ini`、`sql` 等配置或数据示例
- [ ] 没有语言标识但明显是代码的 fenced code block
- [ ] 行内代码无法说明含义、需要通过附近代码块注释帮助理解的示例

### 1.2 不应强行处理的代码块

以下内容通常不直接插入注释：

- JSON 标准格式代码块，因为 JSON 不支持注释；如需解释，改为在代码块前后补充中文说明，或在不改变格式的前提下使用表格解释字段。
- 纯命令输出、报错输出、日志输出；这些内容应保持原样。
- 官方要求逐字复制的配置、密钥、签名、校验值或协议示例。
- 极短且自解释的单行代码；如果加注释只会重复代码本身，可以不加。

---

## 2. 注释增强原则

- **先理解再注释**：必须同时阅读 `{source_file}`、`{content_file}` 和 `{site_file}`。不要只凭中文译文猜测代码含义。
- **注释尽量充分**：示例代码里的关键类、方法、闭包、参数、返回值、链式调用、条件分支、配置键、生命周期钩子、查询条件和副作用，都应尽量补充中文注释。
- **详细但不空洞**：注释要解释“这一行为什么存在、会影响什么行为、读者复制时应关注什么”，不要写“调用方法”“返回数组”这类没有新增信息的注释。
- **不改变代码行为**：除新增注释外，不改变量名、类名、方法名、参数名、配置键、字符串枚举、路由、命令和文件路径。
- **不破坏可复制性**：注释必须使用目标语言支持的语法，并放在不会导致复制执行失败的位置。
- **保留原始意图**：英文源文件已有注释时，优先翻译或中英并列保留其含义；不要删除原本传达技术约束的注释。
- **尊重上下文**：注释应与正文译文的术语保持一致，优先沿用同一页面和相邻页面已有说法。
- **同步双层文件**：增强后的内容必须同步写入 `{content_file}` 和 `{site_file}`，除非有明确记录说明只更新其中一层。

---

## 3. 注释密度要求

代码注释增强阶段可以比普通翻译阶段更积极。建议按以下密度执行：

| 代码类型 | 注释密度 |
|----------|----------|
| 入门示例 | 几乎每个关键调用都加注释，帮助新读者建立概念 |
| 链式 API 示例 | 每 1-3 个链式调用补充一段说明，解释配置效果和组合关系 |
| 闭包 / 回调 | 注明触发时机、参数来源、返回值用途和副作用 |
| UI / 数据结构示例 | 注明字段显示效果、验证规则、状态读写、关系绑定和用户可见文案 |
| 配置文件 | 对关键配置项逐项解释，说明默认值、可选值或启用后的影响 |
| 命令行 | 解释命令用途、参数含义、运行前提和生成结果 |
| 复杂示例 | 在代码块顶部加总体说明，关键步骤前加分段注释，必要时在行尾补充短注释 |

注释不是越机械越好。高密度的标准是“读者读完注释能理解示例为什么这样写”，不是“每一行后面都塞一句重复解释”。

---

## 4. 注释语法规则

按代码块语言选择注释语法：

| 语言标识 | 推荐注释语法 | 注意事项 |
|----------|--------------|----------|
| `php` | `//`、`/* ... */` | 长段说明可放在相关代码前一行，避免打断链式调用或数组结构 |
| `blade` | `{{-- ... --}}`、HTML 中可用 `<!-- ... -->` | 不要把 Blade 注释放进会改变 HTML 输出的位置 |
| `js` / `ts` / `tsx` | `//`、`/* ... */` | JSX 内部说明可用 `{/* ... */}` |
| `css` | `/* ... */` | 不要使用 `//` |
| `bash` / `shell` | `#` | 命令续行中不要把注释放到反斜杠后面 |
| `yaml` / `yml` | `#` | 注意缩进层级，注释应贴近对应键 |
| `env` / `ini` | `#` 或 `;` | 沿用该代码块已有风格 |
| `sql` | `--` | 多行说明可用 `/* ... */` |
| `json` | 不直接加注释 | JSON 不支持注释，改在代码块外解释 |
| 未标识 | 先判断真实语言 | 必要时补上正确语言标识，再按对应语法注释 |

## 5. 单篇执行流程

### 步骤 1：读取并对照三份文件

```bash
sed -n '1,260p' "$SOURCE_FILE"
sed -n '1,260p' "$CONTENT_FILE"
sed -n '1,260p' "$SITE_FILE"
```

检查重点：

- [ ] 中文译文是否已经完成并通过基础校对
- [ ] `{content_file}` 与 `{site_file}` 是否一致
- [ ] 英文源文件的代码块数量、顺序和译文一致
- [ ] 英文源文件是否已有注释、提示语或正文解释可转化为代码注释

如果 `{content_file}` 与 `{site_file}` 不一致，先确认以哪一份为准，再执行注释增强。

### 步骤 2：列出代码块清单

为每个代码块建立临时清单：

| 序号 | 语言 | 主题 | 是否已有注释 | 处理策略 |
|------|------|------|--------------|----------|
| 1 | `ts` | 数据格式化函数 | 少量 | 增加输入来源、回退逻辑和返回值注释 |
| 2 | `bash` | 安装命令 | 无 | 增加命令用途和参数注释 |

处理策略应明确：

- 原注释翻译为中文
- 原注释保留英文并补中文解释
- 新增段落级注释
- 新增行级注释
- JSON / 输出类代码块不加注释，改为代码块外说明

### 步骤 3：理解代码含义

对每个代码块，结合英文源文和中文正文确认：

- [ ] 示例属于哪个功能点
- [ ] 每个类、方法、配置键在示例中承担什么作用
- [ ] 链式调用之间是否存在顺序依赖
- [ ] 闭包参数来自哪里，返回值被谁使用
- [ ] 示例中的用户可见文案是否已按中文读者习惯处理
- [ ] 注释是否会误导读者把示例当成唯一写法

不要凭 API 名称臆测行为。若无法确认含义，应查同目录相邻页面、官方源文上下文或框架文档，再写保守注释。

### 步骤 4：添加中文注释

添加注释时优先采用以下方式：

- 在复杂代码块开头加一段“整体意图”注释。
- 在逻辑阶段前添加块级注释，例如“准备输入数据”“配置校验规则”“根据当前状态生成返回值”。
- 在关键链式调用前或后添加行级注释，说明它对 UI、数据、验证或行为的影响。
- 对闭包补充参数来源、返回值用途和执行时机。
- 对容易复制后需要修改的值，说明读者应替换的位置。

示例：

```ts
type User = {
    name?: string;
    email: string;
};

function formatDisplayName(user: User): string {
    // 优先使用用户主动填写的名称；trim() 可以避免只输入空格时被当成有效名称。
    const normalizedName = user.name?.trim();

    if (normalizedName) {
        // 返回清理后的名称，让界面显示更稳定，也避免保留首尾多余空格。
        return normalizedName;
    }

    // 如果用户没有填写名称，就回退到邮箱；这样调用方始终能拿到可显示的文本。
    return user.email;
}
```

### 步骤 5：同步 content 和 site

完成增强后，必须保证 `{content_file}` 与 `{site_file}` 同步：

```bash
diff -u "$CONTENT_FILE" "$SITE_FILE"
```

如果两者应完全一致，推荐先修改 `{content_file}`，再复制到 `{site_file}`；如果站点文件存在 Docusaurus 专用图片路径或组件转换差异，必须逐项确认差异是有意保留的。

### 步骤 6：局部复查

复查新增注释：

- [ ] 注释语法符合代码块语言
- [ ] 注释没有落在字符串、数组、链式调用或命令续行的非法位置
- [ ] 注释没有改变示例缩进和 Markdown 代码围栏
- [ ] 注释没有把 API、配置键、命令、路径误译成中文
- [ ] 注释与正文解释不冲突
- [ ] 注释足够详细，能帮助读者理解代码意图

## 6. 批量执行流程

批量为多篇文档添加代码注释时，按以下顺序执行：

1. **先确定范围**：列出本轮要处理的 `{content_file}` / `{site_file}` 对，不按目录名猜测完成度。
2. **抽样确认风格**：先处理 1 篇代码较多的文档，确定注释密度、语气和术语风格。
3. **逐篇对照源文**：每篇都读取英文源文件和中文译文，不跨文件套用注释。
4. **逐篇同步双层文件**：每完成一篇，立即同步 `content/` 与 `site/docs/`。
5. **集中运行检查**：完成一批后再执行资源路径、上游专用组件和构建检查。
6. **输出批量报告**：列出处理文件、代码块数量、跳过原因和验证结果。

---

## 7. 验证命令

代码注释增强通常会修改大量 fenced code block，建议至少执行：

```bash
# 检查 site/docs 中是否残留上游资源路径
grep -rn "raw-assets\|docs-assets" "$SITE_DOCS/"

# 检查 site/docs 中是否残留 Docusaurus 不支持的上游组件
grep -rn "@components\|AutoScreenshot\|<Aside\|<Disclosure\|<RadioGroup\|<UtilityInjection" "$SITE_DOCS/"

# 如果修改了站点可见文档，优先做类型和构建验证
cd site
npm run typecheck
npm run build
```

如果只是新增项目工作流文档，没有修改 `site/docs/`，可以不运行 Docusaurus 构建，但应检查 Markdown 链接和文档索引是否更新。

每篇文档完成后，按以下格式输出报告：

```markdown

- 中文归档文件：`{content_file}`
- 站点文件：`{site_file}`

| 项目 | 结果 | 备注 |
```
