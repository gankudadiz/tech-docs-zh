# 03. 翻译校对工作流

**日期**: 2026-05-17
**最近更新**: 2026-05-18
**状态**: 正式

本文档定义翻译完成后的校对流程。校对的目标是：**确保中文译文在内容完整性、翻译准确性、技术正确性三个维度上与英文原文一致**。

校对应在翻译完成后、合并到主分支前进行。每篇文档必须逐项通过后才能标记为"已校对"。

---

## 0.1 执行前变量

校对前先确认变量，后续命令都按变量替换：

| 变量 | 示例 | 说明 |
|------|------|------|
| `{product}` | `filament` | 产品目录名 |
| `{version}` | `v4.x` | 版本目录名 |
| `{source_file}` | `sources/filament/v4.x/normalized/docs/01-introduction/01-overview.md` | 英文源文件 |
| `{content_file}` | `content/filament/v4.x/zh-cn/docs/introduction/overview.md` | 中文归档文件，按官网 URL 结构保存 |
| `{site_file}` | `site/docs/filament/v4.x/introduction/overview.md` | 站点可见文件 |
| `{site_docs}` | `site/docs/filament/v4.x` | 当前产品/版本站点目录 |
| `{sidebar_id}` | `filamentV4Sidebar` | 当前产品/版本 sidebar id |

校对对象通常是 `{content_file}` 与 `{site_file}`。如果两者内容不一致，需要先确认以哪一份为准，不要直接覆盖。`sources/` 可保留 GitHub 官方编号结构，`content/` 与 `site/docs/` 应使用官网 URL 结构。

执行命令前可先设置：

```bash
PRODUCT=filament
VERSION=v4.x
LANG=zh-cn
SOURCE_FILE="sources/$PRODUCT/$VERSION/normalized/docs/01-introduction/01-overview.md"
CONTENT_FILE="content/$PRODUCT/$VERSION/$LANG/docs/introduction/overview.md"
SITE_FILE="site/docs/$PRODUCT/$VERSION/introduction/overview.md"
SITE_DOCS="site/docs/$PRODUCT/$VERSION"
SIDEBAR_ID="filamentV4Sidebar"
```

## 0. 校对原则

- **逐段对照**：校对不是"通读一遍觉得通顺就行"，必须逐段与原文比对。
- **只修不重写**：校对阶段发现的问题应做最小改动，不重新组织段落结构。
- **记录问题**：每个发现的问题都应记录到校对报告中，便于追溯和改进翻译流程。

---

## 1. 内容完整性检查

**目标**：确认译文没有遗漏原文的任何段落、列表项、表格行或提示框。

### 1.1 段落级对比

逐段对比原文和译文，检查：

- [ ] 每个原文段落都有对应的中文译文
- [ ] 列表项数量一致（无遗漏、无多余）
- [ ] 表格行数和列数一致
- [ ] 提示框（`:::info`、`:::tip`、`:::warning`、`:::danger`）数量和内容一致
- [ ] 标题层级一致（`##`、`###`、`####` 等不能跳级或缺失）

### 1.2 常见遗漏点

以下内容容易在翻译时被遗漏：

- 章节末尾的"另见"（See also）链接段落
- 代码块后面的说明文字
- 表格下方的脚注或补充说明
- `<Aside>` / `<Disclosure>` 等组件包裹的附加信息

### 1.3 多余内容检查

检查译文中是否有多余的内容：

- [ ] 不属于该位置的原文句子被错误地合并到此处
- [ ] 翻译时误将其他章节的内容复制过来
- [ ] 重复的段落或句子

---

## 2. 翻译准确性检查

**目标**：确保译文准确传达了原文的技术含义，没有曲解或偏差。

### 2.1 技术术语一致性

对照术语表（`content/glossary/`）检查：

- [ ] 同一术语在全文中使用一致的译法
- [ ] 术语表中的译法被正确使用
- [ ] 没有出现同一概念在不同段落使用不同译法的情况

常见术语对照（Filament）：

| 英文 | 中文 | 备注 |
|------|------|------|
| Resource | 资源 | |
| Action | 操作 | |
| Schema | 模式 | |
| Form | 表单 | |
| Table | 表格 | |
| Infolist | 信息列表 | |
| Notification | 通知 | |
| Widget | 小部件 | |
| Panel | 面板 | |
| Page | 页面 | |
| Relationship Manager | 关联管理器 | |
| Lifecycle Hook | 生命周期钩子 | |
| Authorization | 授权 | |
| Policy | 策略 | |
| Wizard | 向导 | |
| Bulk Action | 批量操作 | |
| Cluster | 集群 | |
| Tenant / Tenancy | 租户 / 多租户 | |

### 2.2 语义准确性

逐句检查关键段落：

- [ ] 方法说明准确描述了方法的行为（不是猜测）
- [ ] 参数说明与原文一致
- [ ] 返回值说明与原文一致
- [ ] 条件逻辑（if/else、when/unless）翻译准确，没有反转
- [ ] 否定句没有被翻译为肯定句（或反之）

### 2.3 语气和风格

- [ ] 技术文档应使用陈述语气，不用感叹句
- [ ] 保持原文的正式/非正式风格一致
- [ ] 中文表达自然流畅，不是生硬的逐字翻译

---

## 3. 代码块完整性检查

**目标**：确保代码块未被误翻译，且完整保留。

### 3.1 绝对不能翻译的内容

以下内容必须保持英文原文：

- [ ] 变量名、函数名、方法名、类名
- [ ] 命令行命令和参数
- [ ] 配置键名和配置值
- [ ] 文件路径和文件名
- [ ] URL 和路由路径
- [ ] CSS 类名和选择器
- [ ] SQL 语句
- [ ] JSON / YAML 键名

### 3.2 代码注释处理

代码块中的注释处理规则：

- **代码示例中的注释**：保持英文原文不翻译。理由：
  - 代码块是开发者直接复制使用的，注译为中文会增加使用摩擦
  - 英文注释与代码上下文更一致
  - 避免因翻译导致注释与代码逻辑不符
- **例外**：如果注释是解释性的说明文字（非代码逻辑注释），且翻译后对中文读者有明显帮助，可以在注释下方用中文补充说明，但原始英文注释必须保留

### 3.3 代码块格式

- [ ] 代码块语言标识正确（`php`、`bash`、`blade`、`ini`、`env` 等）
- [ ] 代码块内的缩进和空行与原文一致
- [ ] 没有因翻译过程导致的代码块断裂（一个代码块被拆成多个）

---

## 4. 组件与语法兼容性检查

**目标**：确保译文中不包含目标平台不支持的组件或语法。

### 4.1 Astro 组件处理

上游 Filament 文档使用 Astro 框架，以下组件在 Docusaurus 中不可用，必须转换：

| Astro 组件 | Docusaurus 替代方案 |
|-----------|-------------------|
| `import AutoScreenshot from "@components/AutoScreenshot.astro"` + `<AutoScreenshot name="X" alt="Y" version="..." />` | `![Y](/assets/{product}/{version}/screenshots/images/light/X.jpg)` |
| `<Aside variant="info">...</Aside>` | `:::info ... :::` |
| `<Aside variant="tip">...</Aside>` | `:::tip ... :::` |
| `<Aside variant="warning">...</Aside>` | `:::warning ... :::` |
| `<Aside variant="danger">...</Aside>` | `:::danger ... :::` |
| `<Disclosure>` | 需评估是否可用 `<details>` 替代，或改为普通段落 |
| `<RadioGroup>` / `<RadioGroupOption>` | 不支持，改为线性文档结构 |
| `<UtilityInjection>` | 不支持，改为纯文本说明 |

### 4.2 检查清单

- [ ] 没有残留的 `import ... from "@components/..."` 语句
- [ ] 没有残留的 `<AutoScreenshot`、`<Aside`、`<Disclosure`、`<RadioGroup` 等 Astro 组件标签
- [ ] `:::info` / `:::tip` / `:::warning` / `:::danger` 语法格式正确（前后有空行）
- [ ] MDX 语法兼容（Docusaurus 使用 MDX，不支持所有 HTML 标签）

### 4.3 快速检查命令

```bash
# 检查是否有残留的 Astro 组件
grep -rn "@components\|AutoScreenshot\|<Aside\|<Disclosure\|<RadioGroup\|<UtilityInjection" "$SITE_DOCS/"

# 检查是否有未闭合的自定义容器
grep -rn "^:::" "$SITE_DOCS/" | grep -v "^.*:::.*$"
```

## 5. 图片资源检查

**目标**：确保所有图片引用正确，图片文件存在。

### 5.1 图片路径格式

站点中的图片必须使用绝对路径：

```
/assets/{product}/{version}/screenshots/images/light/{category}/{filename}.jpg
```

不允许出现：

- 相对路径（`../../raw-assets/...`）
- `raw-assets` 或 `docs-assets` 残留
- Astro 组件引用（`<AutoScreenshot>`）

### 5.2 检查清单

- [ ] 所有图片路径以 `/assets/` 开头
- [ ] 没有 `raw-assets` 或 `docs-assets` 残留
- [ ] 图片文件存在于 `site/static/assets/` 对应目录
- [ ] 图片 alt 文本已翻译为中文

### 5.3 验证命令

```bash
# 检查残留的原始路径
grep -rn "raw-assets\|docs-assets" "$SITE_DOCS/"

# 检查图片文件是否存在
grep -rP '!\[.*?\]\(\K[^)]+' "$SITE_DOCS/" | while read file; do
  filepath=$(echo "$file" | cut -d: -f1)
  imgpath=$(echo "$file" | cut -d: -f2 | tr -d ' ')
  [ -f "site/static${imgpath}" ] || echo "MISSING: ${imgpath} (in ${filepath})"
done

# 列出所有引用的图片
grep -rP '!\[.*?\]\(/assets/[^)]+\)' "$SITE_DOCS/" -o | sort -u
```

---

## 6. 链接检查

**目标**：确保内部链接指向正确的站内路径，外部链接保留原文。

### 6.1 内部链接

- [ ] 已翻译文档的链接指向正确的站内路径
- [ ] 未翻译文档不要假设已有占位页；如果需要站内跳转，必须创建明确占位页或记录为已知 broken link
- [ ] 锚点链接（`#section-id`）与目标标题的生成 ID 匹配
- [ ] 没有指向 `sources/` 或 `content/` 目录的链接

### 6.2 外部链接

- [ ] 外部链接保持原文 URL，不修改
- [ ] Laravel 官方文档链接保持原样
- [ ] GitHub 链接保持原样

### 6.3 验证命令

```bash
# 检查是否有指向 sources 或 content 的错误链接
grep -rn '\](.*sources/\|\](.*content/' "$SITE_DOCS/"

# 列出所有内部链接
grep -rP '\]\((?!http|/assets)[^)]+\)' "$SITE_DOCS/" -o | sort -u
```

## 7. Frontmatter 检查

**目标**：确保文档元数据正确。

### 7.1 检查清单

- [ ] `title` 字段已翻译为中文
- [ ] `title` 值不包含多余的引号或特殊字符
- [ ] `contents: false` 保留（仅原文中有的文件）
- [ ] 没有遗漏的 frontmatter 字段

### 7.2 常见错误

```yaml
# 错误：title 未翻译
---
title: Creating records
---

# 错误：title 多余引号
---
title: "创建记录"
---

# 正确
---
title: 创建记录
---
```

---

## 8. 构建验证

**目标**：确保站点能正常构建，页面能正常访问。

### 8.1 构建检查

```bash
cd site && npm run build
```

构建过程中关注：

- [ ] 没有 `Module not found` 错误
- [ ] 没有 `MDX compilation failed` 错误
- [ ] 没有 `couldn't be resolved to an existing local image file` 错误
- [ ] broken link / anchor 警告是否为已知的未翻译页面（可接受）

### 8.2 页面访问检查

本项目通常由用户提前启动本地 Docusaurus 服务。Agent 不应在修改后自动运行 `npm run start`。

访问检查规则：

- 如果用户已有服务，提示用户刷新目标页面。
- 如果页面仍显示旧内容，提示用户手动重启已有服务。
- 只有用户明确要求启动服务时，才从 `site/` 执行 `npm run start`。

- [ ] 页面正常加载，无白屏
- [ ] 图片正常显示
- [ ] 代码块有语法高亮
- [ ] 侧边栏显示正确的标题
- [ ] 内部链接可正常跳转

---

## 9. 侧边栏检查

**目标**：确保新增文档在正确产品/版本的侧边栏中显示，且不破坏左侧导航作用域和版本切换入口。

- [ ] 已在 `site/sidebars.ts` 中添加文档 ID
- [ ] 文档 ID 与文件路径匹配（去掉 `.md`，相对于 `site/docs/`）
- [ ] 文档添加在正确的产品/版本 sidebar 中，例如 `{sidebar_id}`
- [ ] 所属分类正确
- [ ] 排序位置合理（与同分类其他文档的逻辑顺序一致）
- [ ] 左侧顶层仍是章节分类，没有重新出现 `中文技术文档站`、`文档` 或产品名外层分类
- [ ] 新增产品或版本时，已同步 `site/src/data/docsCatalog.ts` 中的产品/版本、默认入口、来源链接和 sidebar id
- [ ] 同一产品的新版本没有新增首页并列产品卡片，而是出现在产品卡片和顶部版本下拉中

## 11. 批量校对流程

当一次翻译了多篇文档时，按以下顺序批量校对：

1. **先跑构建**：`npm run build`，快速发现编译级错误
2. **修复编译错误**：优先解决 `Module not found`、图片缺失等阻断性问题
3. **逐篇内容校对**：按第 1-7 节逐篇检查
4. **再跑构建**：确认所有修复后构建通过
5. **页面访问验证**：提示用户刷新已有页面；只有用户明确要求时才启动服务
6. **输出校对报告**：汇总所有问题和处理结果

## 12. 校对分工建议

| 校对类型 | 适合谁做 | 关注点 |
|---------|---------|--------|
| 内容完整性 | AI 辅助 | 逐段对比，不遗漏 |
| 翻译准确性 | 人工 | 术语、语义、语气 |
| 代码块完整性 | AI 辅助 | 自动化检查翻译残留 |
| 组件兼容性 | AI 辅助 | 自动化检查 Astro 组件残留 |
| 图片资源 | AI 辅助 + 人工 | 路径检查 + 目视确认图片显示 |
| 链接 | AI 辅助 | 自动化检查路径正确性 |
| 构建验证 | 自动化 | `npm run build` |
| 侧边栏 | 人工 | 目视确认侧边栏显示 |
