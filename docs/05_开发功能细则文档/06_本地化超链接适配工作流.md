# 06. 本地化超链接适配工作流

**日期**: 2026-05-22
**状态**: 正式

本文档定义本地化文档中的超链接适配流程。目标是：**让译文里的内部链接指向当前 Docusaurus 站点中真实存在、可访问、语义正确的本地页面或锚点**。

本流程适用于翻译、校对、批量修复 broken links、从官方文档同步新页面后整理链接，以及发现某个页面在本地开发服务器中跳转失败时的专项修复。

---

## 0. 执行前变量

执行前先确认变量，后续命令都按变量替换：

| 变量 | 示例 | 说明 |
|------|------|------|
| `{product}` | `filament` | 产品或框架目录名 |
| `{version}` | `v4.x` | 版本目录名 |
| `{lang}` | `zh-cn` | 翻译语言 |
| `{content_file}` | `content/filament/v4.x/zh-cn/docs/infolists/overview.md` | 中文归档文件 |
| `{site_file}` | `site/docs/filament/v4.x/infolists/overview.md` | 站点可见文件 |
| `{site_docs}` | `site/docs/filament/v4.x` | 当前产品/版本站点目录 |
| `{site_route_prefix}` | `/docs/filament/v4.x` | 当前产品/版本的浏览器路由前缀 |

执行命令前可先设置：

```bash
PRODUCT=filament
VERSION=v4.x
LANG=zh-cn
CONTENT_FILE="content/$PRODUCT/$VERSION/$LANG/docs/infolists/overview.md"
SITE_FILE="site/docs/$PRODUCT/$VERSION/infolists/overview.md"
SITE_DOCS="site/docs/$PRODUCT/$VERSION"
SITE_ROUTE_PREFIX="/docs/$PRODUCT/$VERSION"
```

---

## 1. 适用范围

优先处理这些链接：

- [ ] 指向同一产品/版本内其他文档页的相对链接。
- [ ] 从官方文档迁移而来的绝对路径、缺少版本段的路径或旧路由。
- [ ] 指向目录但本地没有 `index.md` 的链接。
- [ ] 指向官方页面 slug，但本地采用了不同目录或文件名的链接。
- [ ] 带锚点的内部链接，例如 `../resources/overview#creating-a-resource`。
- [ ] Docusaurus build 或浏览器点击发现的 broken link。

通常不处理这些链接：

- 外部链接，例如 GitHub、Laravel、Livewire、Composer、npm 等官方地址。
- `mailto:`、`tel:`、`#` 当前页锚点，除非锚点本身已确认失效。
- 图片链接，图片路径按翻译操作指南中的资源规则处理。
- 指向尚未接入本地站点的官方页面；这类链接应保留外部官方 URL，或明确记录为已知未接入页面。

---

## 2. 本地路由判断规则

Docusaurus 站点实际读取 `site/docs/{product}/{version}/`。一般情况下：

| 本地文件 | 浏览器路径 |
|----------|------------|
| `site/docs/filament/v4.x/resources/overview.md` | `/docs/filament/v4.x/resources/overview` |
| `site/docs/filament/v4.x/actions/modals.md` | `/docs/filament/v4.x/actions/modals` |
| `site/docs/filament/v4.x/index.md` | `/docs/filament/v4.x/` |

判断链接是否可用时，以本地文件和 Docusaurus build 结果为准，不要只看官方 URL。

常见适配场景：

| 官方或旧链接 | 本地应检查的方向 |
|--------------|------------------|
| `/docs/resources`、`resources` | 本地是否存在 `resources/overview.md` 或对应具体页面 |
| `/docs/action`、`action` | 本地是否实际使用 `actions/...` |
| 指向目录的链接 | 目录下是否存在 `index.md`，否则应指向具体页面 |
| 官方页面 slug | 本地 `site/docs/` 是否沿用了同一 slug |

## 3. 单篇页面修复流程

### 步骤 1：抽取当前页面链接

```bash
rg -n "\\[[^]]+\\]\\([^)]+\\)|href=\\\"[^\\\"]+\\\"" "$SITE_FILE"
```

检查每个链接：

- [ ] 链接文字是否仍然符合中文语境。
- [ ] 链接目标是站内、站外、锚点还是图片。
- [ ] 站内链接是否指向当前产品和版本。
- [ ] 站内链接是否能映射到真实的 `site/docs/` 文件。

### 步骤 2：确认本地候选页面

对可疑链接，不要凭感觉改。先查本地真实文件：

```bash
find "$SITE_DOCS" -type f | sort | rg "resources|actions|relation|modal|overview"
```

如果链接文字是中文译文，需要结合上下文反推英文概念，再在本地文件名中找对应页面。

例如：

- “面板资源”通常应先查 `resources/overview.md`。
- “关联管理器”通常应先查 `resources/managing-relationships.md` 或相关 relation 页面。
- “操作模态框”通常应先查 `actions/modals.md`，不要直接假设存在 `/action`。

### 步骤 3：选择修复方式

按以下优先级处理：

1. 已有对应本地页面：改为本地真实路由或相对路径。
2. 已有对应页面但锚点不同：改为真实页面，并修正锚点。
3. 本地尚未接入但短期会接入：可创建明确的“翻译中”占位页，并更新 `site/sidebars.ts`。
4. 本地不准备接入：保留官方外部链接，或在修复记录中标记为已知未接入链接。

不要做这些事：

- 不要把链接指向 `sources/` 或 `content/`。
- 不要为了消除 broken link 随便指向相近但语义错误的页面。
- 不要把所有官方链接机械替换成同名本地路径。
- 不要只改 `site/docs/` 而忘记同步 `content/`。

### 步骤 4：同步修改双层文件

同一处链接修复通常需要同步修改：

```text
content/{product}/{version}/{lang}/docs/...
site/docs/{product}/{version}/...
```

除非有明确记录说明某个链接只影响站点层，否则 `content_file` 和 `site_file` 应保持一致。

## 4. 批量检查流程

### 步骤 1：自动扫描连字符→下划线错误（推荐）

这是最常见的链接问题——Docusaurus 路由保留文件名中的下划线，但链接常错误使用连字符。使用 `scripts/fix_underscore_links.py` 自动检测和修复：

```bash
# 预览模式，先看有哪些问题
python3 scripts/fix_underscore_links.py "$SITE_DOCS" --dry-run

# 实际修复（site/ 和 content/ 双目录同步）
python3 scripts/fix_underscore_links.py "$SITE_DOCS" "content/$PRODUCT/$VERSION/$LANG/docs/"
```

此脚本会自动扫描所有带下划线的文件名，生成连字符→下划线映射，并替换所有不对应的内部链接。

### 步骤 2：列出站内链接（手动复查）

```bash
rg -n "\\[[^]]+\\]\\((/docs/|\\.\\.?/|[^)#]+\\.md|[^)#]+/)[^)]+\\)" "$SITE_DOCS"
```

### 步骤 3：查找明显错误目标

优先查这些高风险模式：

```bash
rg -n "\\]\\((/docs/)?(action|resource)(/|\\)|#)" "$SITE_DOCS"
rg -n "\\]\\([^)]*raw-assets|\\]\\([^)]*sources/|\\]\\([^)]*content/" "$SITE_DOCS"
```

### 步骤 4：运行构建验证

结构性链接修改后，从 `site/` 运行：

```bash
npm run build
```

如果构建报告 broken links / broken anchors：

- [ ] 先判断是否为本轮新增或修改引入。
- [ ] 本轮引入的问题必须修复。
- [ ] 既有未接入页面可以记录为已知问题，但不能误报为已修复。

## 5. 修复记录模板

完成一轮链接适配后，在回复或工作记录中说明：

```text
本地化超链接适配记录

- 页面：site/docs/{product}/{version}/...
- 同步文件：content/{product}/{version}/{lang}/docs/...
- 修复链接：
  - “面板资源”：旧目标 `...` -> 新目标 `...`
  - “操作模态框”：旧目标 `...` -> 新目标 `...`
- 未处理链接：
  - `...`：本地尚未接入，保留官方外链 / 记录为已知 broken link
- 验证：
  - npm run build：通过 / 未运行 / 存在既有 broken links
```

---

## 6. 最小验收清单

- [ ] 所有本轮修改过的站内链接都能映射到本地真实页面。
- [ ] 锚点链接已确认目标标题存在，或已改成不带锚点的稳定页面链接。
- [ ] 没有新增指向 `sources/`、`content/`、`raw-assets` 的链接。
- [ ] `content/` 与 `site/docs/` 已同步。
- [ ] 必要时已运行 `npm run build`，并确认 broken links 是否为本轮引入。
