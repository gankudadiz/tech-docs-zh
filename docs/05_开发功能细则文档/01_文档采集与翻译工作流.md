# 01. 文档采集与翻译工作流

**日期**: 2026-05-16  
**最近更新**: 2026-05-17  
**当前状态**: 正式

本文档用于确定官方文档如何采集、快照如何保存、资源如何归档，以及采集结果如何进入后续翻译流程。执行具体翻译时继续阅读 `02_翻译操作指南.md`；新增产品或版本时继续阅读 `04_新增产品或版本接入工作流.md`。

如果处理的是 Filament v4.x，必须同时阅读 `源文件结构详解/Filament_v4x_官方GitHub源文件结构详解.md`。Filament v4.x 的官网文档不是只由仓库根 `docs/` 生成，还包含 `packages/*/docs`，且 `docs/04-_PACKAGES` 是官方构建时的包文档插入占位。

## 1. 总原则

优先拿“结构化原文”，再考虑抓网页，最后才手工复制。

原因是技术文档通常包含代码块、告警框、组件示例、图片、页内锚点、跨页链接。直接从浏览器保存或复制，容易丢失结构，也不利于后续同步官方更新。

采集时使用统一路径变量：

| 变量 | 示例 | 说明 |
|------|------|------|
| `{product}` | `filament` | 产品目录名 |
| `{version}` | `v4.x` | 版本目录名 |
| `{upstream}` | `sources/_upstream/filament-4.x-docs` | 可选的上游工作副本 |
| `{raw_docs}` | `sources/filament/v4.x/raw/docs` | 原始文档快照 |
| `{raw_assets}` | `sources/filament/v4.x/raw-assets` | 原始资源快照 |
| `{normalized_docs}` | `sources/filament/v4.x/normalized/docs` | 清洗后的可翻译文档 |

## 2. 推荐来源优先级

### 2.1 官方文档源码仓库

这是最推荐的方式。

很多技术文档本身就是开源仓库里的 Markdown、MDX、VuePress、VitePress、Docusaurus 或 Astro 内容。优先找：

- GitHub 仓库。
- 文档目录，例如 `docs/`、`website/docs/`、`apps/docs/`。
- 图片和静态资源目录，例如 `public/`、`static/`、`assets/`。
- 对应版本 tag 或分支。
- License 文件和贡献说明。

对于 monorepo，不能只记录第一个看起来像文档的目录。需要继续检查是否存在 `packages/*/docs`、`apps/*/docs`、`website/*/docs` 等分散文档源，并确认官网是否会把它们合并到同一套文档导航中。

优点：

- 原文结构完整。
- 代码块、标题、链接、图片路径更可靠。
- 更容易按版本同步。
- 可以通过 Git diff 追踪官方更新。

### 2.2 官方提供的原始文档包或文本接口

如果官方提供 Markdown 下载、版本压缩包、`llms.txt`、`llms-full.txt`、API 文档 JSON、OpenAPI schema 等结构化入口，也可以优先使用。

这些内容通常比 HTML 页面更适合翻译和二次整理。

### 2.3 受控爬取官方页面

当没有源码或结构化入口时，再考虑爬取。

爬取策略必须保守：

- 先确认 robots、许可和使用条款。
- 优先从 sitemap 或明确的文档路由列表开始。
- 限定产品、版本和路径范围。
- 设置低频率请求。
- 只提取正文区域，不抓导航、广告、脚本噪音。
- 保存原始 HTML 快照和清洗后的 Markdown/MDX。
- 每次采集生成 manifest，记录 URL、时间、状态码、内容 hash。

如果页面依赖前端渲染，再考虑 Playwright；否则优先普通 HTTP 获取，速度更快，也更稳定。

### 2.4 浏览器右键另存为 HTML

适合临时样本，不适合长期维护。

可用场景：

- 只验证一篇页面的结构。
- 目标站反爬或动态渲染导致脚本暂时拿不到正文。
- 想快速保存某个页面作为对照样本。

不推荐作为主流程，因为浏览器保存的 HTML 通常会混入大量运行时代码、随机资源名和页面噪音。

### 2.5 手工复制

适合少量难处理段落，不适合整站。

可用场景：

- 只翻译一小段说明。
- 某个示例需要人工重排。
- 官方页面结构混乱，自动清洗结果不可信。

如果一整套文档都靠人工复制，会很难同步官方更新。

## 3. 图片和资源处理

优先从官方源码仓库获取图片资源；如果只能从 HTML 获取，则下载正文中实际引用的资源。

资源存放建议：

```text
sources/{product}/{version}/raw-assets/
content/{product}/{version}/assets/
```

处理规则：

- 不热链官方图片。
- 保留原始文件名和来源 URL。
- 为每个资源记录 hash，避免重复下载。
- 图片含英文 UI 时，优先保留原图，并在译文中解释；只有确有必要时再制作中文标注图。
- 不复制官方 logo、专有插画、品牌装饰，除非许可明确允许。
- **上游文档可能使用框架特定组件引用图片（如 Astro 的 `AutoScreenshot`），翻译时必须转换为标准 Markdown 图片语法。** 详见 `02_翻译操作指南.md` 第 7 节。
- **图片文件必须从上游源码复制到 `site/static/assets/` 目录，否则构建时会报错。**

站点资源最终位置：

```text
site/static/assets/{product}/{version}/
```

站点正文中的图片引用必须使用：

```text
/assets/{product}/{version}/...
```

## 3.1 manifest 要求

每次新增产品或版本时，应创建：

```text
sources/{product}/{version}/manifest.yml
```

建议字段：

```yaml
product: filament
version: v4.x
source:
  repo: https://github.com/filamentphp/filament
  ref: 4.x
  docs_path: docs
  assets_path: docs-assets
retrieved_at: YYYY-MM-DD
license: 待确认
notes:
  - 记录 sparse checkout、清洗范围或已知缺失资源
```

manifest 是后续同步官方更新和排查版本差异的依据，不要省略。

## 4. 翻译流程

推荐流程：

```text
原文获取 -> manifest -> 结构清洗 -> 术语表匹配 -> AI 初译 -> content 归档 -> site 入站 -> 校对 -> 构建检查
```

翻译规则：

- 代码块默认不翻译。
- 命令、参数、类名、函数名、组件名、配置键不翻译。
- API 名称首次出现可保留英文，并补中文解释。
- 标题翻译要服务于搜索和目录浏览，不追求逐字对应。
- 同一产品同一概念使用固定译名。
- 对官方含糊或版本差异较大的地方，保留原文链接和译注。

## 5. 术语表

建议后续新增：

```text
content/glossary/
├── common.yml
├── laravel.yml
├── filament.yml
├── tailwindcss.yml
└── daisyui.yml
```

示例：

```yaml
resource:
  zh: 资源
  note: Filament 中通常保留“资源”译法。
policy:
  zh: 策略
  note: Laravel 授权上下文中使用“策略”。
```

## 6. 质量检查

每篇译文进入正式站点前至少检查：

- 页面能被本地构建。
- 标题层级没有断裂。
- 内链指向当前产品和当前版本。
- 外链保留官方来源。
- 图片路径存在。
- 代码块没有被误翻译。
- 专有名词符合术语表。
- frontmatter 有来源和翻译状态。

每次采集或新增版本后至少检查：

- `sources/{product}/{version}/manifest.yml` 存在。
- `raw/docs`、`raw-assets`、`normalized/docs` 的职责清楚。
- `normalized/docs` 中没有无法解释的上游运行时代码。
- 后续 `site/docs` 的图片路径不会直接复用 `raw-assets` 相对路径。
- 如果只接入部分页面，已记录范围和缺失页面。

## 7. 版权和许可边界

技术文档翻译通常属于基于原文的衍生内容。即使本项目当前只在本地使用，也应保留来源、许可和采集时间。

如果后续准备公开发布，需要逐个确认产品文档的授权条款，不能默认所有官方文档都允许全文转载和翻译发布。
